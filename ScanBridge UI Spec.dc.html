SCANBRIDGE · ANDROID

UI Specification
& Component Inventory

v1.0 · Aug 2026
Design system: Nocturne
Target: Android / Jetpack Compose

This document specifies the visual and interaction layer for ScanBridge — the Android barcode scanner that pairs with a Windows host over WebSocket and types each scan into the focused field on that PC. It is written to be handed to an implementer (human or coding agent) alongside the interactive prototypes. The app's existing logic — pairing, socket lifecycle, queueing, ML Kit analysis, update checks — is unchanged. Only the presentation layer is respecified.

1 · Foundations

Barcode payloads and timestamps are always monospace — that is the app's data voice. Persian numerals in UI copy, Latin numerals inside code payloads.

1.3 Geometry, spacing, motion

  • Radii: 10dp icon tile · 14dp list row · 16dp card · 18–22dp hero/sheet · 30dp tab bar · full round for pills and the tab circles.
  • Screen padding 18dp; gap between rows 8dp; between sections 20–24dp; bottom content padding 100dp to clear the floating bar.
  • Elevation is an edge plus ambient darkness — 1dp border + a single soft shadow. Never stack shadows.
  • Motion: screen enter = 300ms fade; sheets and cards = 280ms rise 18dp with a decelerate curve; the scan line loops 2.4s ease-in-out; the live dot pulses 1.8–2s.
  • Minimum touch target 48dp. Tab circles are 52dp, scanner controls 40dp inside a 48dp box.

1.4 Localization

Persian is the default and is fully RTL: the layout direction flips, chevrons and back arrows mirror, and all edge insets use start/end rather than left/right. Language switches live in the User panel; the change applies instantly without restart. Keep every string in resources — no literals in composables.

2.1 Scanner — two approved layouts

A · Faithful. Mirrors the current composition: stacked header → connection card → square camera box → last-scan card. Chrome and camera are separate, so status is legible at a glance and the camera is a bounded object. Recommended default.

B · Overlay. The camera fills the tab; status, scan speed, torch and the last scan become floating glass chips over it. Roughly 40% more read area and a calmer screen, at the cost of contrast on bright labels. Ship as a preference if operators are scanning small or distant codes.

Both keep identical controls and identical state semantics. Do not mix them per-user without persisting the choice.

4 · Implementation order

  1. Theme first. Replace Color.kt and the dark scheme in Theme.kt with §1.1, and the type scale in Type.kt with §1.2. Because the app reads MaterialTheme.colorScheme throughout, this alone delivers most of the visual change with zero risk to logic.
  2. Shared components. Build the inventory in §3 as small stateless composables in a ui/components package. No business logic inside them; every one takes data plus callbacks.
  3. Screens, one at a time. Re-lay each screen from §2 using those components, in order: USER_PANEL → HISTORY → SCANNER → PAIRING → INTRO (lowest risk to highest). Leave view-model and socket code untouched.
  4. States pass. Walk §2.2 on a real pairing with the Windows host, including pulling the network cable mid-scan.
  5. RTL pass. Force Persian and check every mirrored inset, chevron and arrow.

Do not rewrite the app. The current implementation already owns pairing, the socket lifecycle, offline queueing, ML Kit analysis and update checks. This specification is a re-skin plus a component extraction — scoped to theme files, a new components package, and the body of each screen composable.
